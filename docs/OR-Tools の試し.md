# OR-Tools（CP-SAT）の試しの案（第1版）

いまの計算の部品（HiGHS）のかわりに、Google の OR-Tools の CP-SAT を使えるかを、測って決めるための案です。
利用者が「OR-Tools（CP-SAT）で作ってみる」と決めた（2026-10-31、確かめ役から）。6-2（じっくり作る）は止め、先にこれを測ります。
枝 `try-ortools`（v6 の 6c99306 の上）。**段1 ではアプリを変えません**（道具と測りだけ）。main と Pages は変えません。

---

## 0. まとめ

- 段1：いまの式（build.js が HiGHS に渡す LP の文）を、そのまま CP-SAT の形に移して node で解き、HiGHS の「1分で作る」と比べます。
- 段2：段1 で「採る」に届いたときだけ、ブラウザで動くかを確かめます。
- 決め方（確かめ役が決めた。測る前）：
  - 採る：次の2つを両方満たすとき。
    - 18か月 × 3回で、CP-SAT（Worker 4・60秒）が HiGHS の「1分で作る」より並べる順で悪い回が無い（絶対・6連勤以上が増えない）。かつ、できれば の平均が2割以上少ない。
    - ブラウザでも、node とほぼ同じ答えが出る（段2）。
  - 採らない：上に届かないとき、またはブラウザで安定して動かないとき。6-2 を予定どおり HiGHS で続けます。
  - どちらになっても、6-1 の仕上げの入れ替えはそのまま使います。
- 「悪い回が無い」の数え方（作り手の案。確かめ役が直してよい）：月ごとに、CP-SAT の 1〜3回目と HiGHS の 1〜3回目を組にした 54組で、CP-SAT が並べる順で悪い組が 0。あわせて「CP-SAT のいちばん悪い回 と HiGHS のいちばん良い回」の比べも報告します。

## 2. 式の移し方（LP の文 → CP-SAT）

- 入れるもの：build.js の `model.lp(段の式, 前の段の上限)` が作る LP の文そのもの。HiGHS と全く同じ式になります（式の作りまちがいを2つの部品で同じに持つため）。
- 道具 `tools/lp-to-cpsat.mjs`：この LP の文（Minimize・Subject To・Binary・End だけを使う、こちらで作る形）を読み、CP-SAT の式にします。
  - 2択の変数 → 0〜1 の整数。
  - 量の変数（違反の量・公休の不足など。LP では 0 以上の数）→ 0 以上の整数。上限は、その変数が出てくる式から決めます（例：「z ≧ 式」なら、式のいちばん大きい値）。決められないときは、その月の日数 × 人数。
- **整数でない所と、どう整数にしたか**（build.js を読んで分かったもの）

| 所 | 整数でない数 | 整数にするやり方 |
|---|---|---|
| 有給の日数のずれ（`paidDiff`） | 半休は有給 0.5 日・設定の有給の日数が 4.5 日など | その式を2倍する。ずれの量の2つの変数（多い・少ない）を「半日の数」にする（いまの量 = その数 ÷ 2） |
| 「できれば」の段の余り日の重み（`_spare`） | 0.5 | 「できれば」の段の式全体を2倍する（ずれの量の半日の数は、2倍したので重み 1） |
| 前の段の上限 | LP では `最小値 + 0.000001` | 整数にした式で「≦ 最小値」（ぴったり） |
| 変わるマスの重み（`_change` 0.001）・責任者の重み（`leaderWeight`） | 1分で作るでは使わない | 段1 では入れない（出てきたら止めて知らせる） |

  - 道具は、移したあとの式の係数がどれも整数かを確かめ、整数でないものが残っていたら止めます。
- 段の順：HiGHS と同じ6段（6連勤以上 → 人員不足 → 公休 → 連勤 → ほかの絶対 → できれば）。
  - 各段のあとで「その段の量 ≦ 見つけたいちばん小さい値」を足して、次の段へ進みます。
  - 前の段の答えは、ヒント（`solution_hint`）として渡します。
- 時間の配分：HiGHS と同じ（段1 は合計の 1/6、段2〜5 は合わせて 1/2、残りを「できれば」の段）。
  - 時間内に「これ以上は無い」と言えた段は「解ききった」、そうでない段は「時間切れ」として記録します。
  - 時間内に答えが1つも無ければ、前の段の答えのままにします（HiGHS と同じ守り）。
- 答えは、build.js の `readTable`（変数の名前 → 値）で表にし、check.js で数えます（HiGHS と同じ道）。
- 式が正しく移ったかの確かめ：小さな月（8〜15人・調べる数で区切って HiGHS が「解ききった」段）で、CP-SAT の各段の最小値が HiGHS の最小値と同じか（式の量 ＝ 式の量）。

## 3. 道具（node）

- `node tools/cpsat.mjs 保存したファイル.json [--workers 4] [--time 60] [--out フォルダ]`
  - 出すもの：段ごとの結果（解ききったか・量・秒）、できた表（取り込める JSON）、`count.mjs` と同じ形の数、使ったメモリのいちばん多い所（0.5秒ごとに `process.memoryUsage().rss` を見る）、CP-SAT に渡した式（段ごとの JSON。Python で同じ式を解くため）。
- `node tools/cpsat-bench.mjs`：下の 4 章の測りを回し、全部の答えを保存して、比べの表を作ります。
- `python tools/cpsat_native.py 段ごとの式.json`：同じ式を、Python の ortools（ふつうのパソコン用）で解きます。速さを比べるためだけです。

## 4. 測り

**月**：説明書の測り C と同じ 18か月です。
- 見本3つ × 2026年11月・2027年2月・5月・8月。
- 作り物 6通り：
  - 8人×2027年2月（28日）・15人×2026年11月（30日）・25人×2026年12月（31日）・50人×2026年12月（31日）。この4つは希望も固定も無い月です（solve-bench --sizes と同じ作り方）。
  - 人手が足りない月：8人×2026年11月（人員不足が 60件ほど出る月）。
  - 希望のある月：20人×2027年5月（make-sample の希望を残す）。

**作るもの**

| 名前 | 中身 | 回数 |
|---|---|---|
| H | HiGHS の「1分で作る」（ほかに何も動かしていないとき。60秒） | 3回 |
| H＋仕上げ | H の答えに 6-1 の仕上げ（上限 25秒） | 3回 |
| C4 | CP-SAT Worker 4・60秒 | 3回（決め方に使う） |
| C4＋仕上げ | C4 の答えに 6-1 の仕上げ | 3回 |
| C1・C2・C8 | CP-SAT Worker 1・2・8・60秒 | 1回ずつ（報告だけ） |
| C4-600 | CP-SAT Worker 4・600秒 | 1回（報告だけ） |

- 同時に動かすのは、合わせて 8本（8コア）までにします。H は「ほかに何も動かしていないとき」なので、H を回すあいだは H だけを1つずつ動かします。
- 時間の見込み：H 18×3×1分 ≒ 1時間、C4 18×3×1分 ÷ 2 ≒ 30分、C1・C2・C8 ≒ 40分、C4-600 18×10分 ÷ 2 ≒ 1時間半。合わせて 4時間ほど。

**報告に書くもの**
- 月ごとの 6連勤以上・絶対・できれば の件数（H・H＋仕上げ・C4・C4＋仕上げ・C1・C2・C8・C4-600）。
- 並べる順で、C4 と H を比べた 良い・同じ・悪い の回数（54組）。C4＋仕上げ と H＋仕上げ も同じく。
- 時間内に答えが出なかった回数（段1 で答えが無い）、使ったメモリのいちばん多い所。
- C4 の答えにも仕上げをかけたら、さらに減るか。
- （時間があれば）Python の ortools で同じ式を解いた速さ。WASM がどれだけ遅いか。

## 5. 段2（段1 で「採る」に届いたときだけ）

確かめ役の文のとおりに確かめます。
- GitHub Pages では COOP/COEP を付けられないので、`coi-serviceworker`（MIT）のような方法で付けられるか。初めて開いたときの読み込み直しの見せ方。オフラインで動くか。
- 付けられないとき（ほかの場所に置いた・古いブラウザ）に1本だけで動くか。動かないなら HiGHS で作る（利用者には同じボタンのまま）。
- Chromium・Edge・Firefox（できれば Safari）。ダウンロードの大きさ（MB）と、2回目から開く速さ。
- データを外に送らないこと：
  - `server` を使わない。
  - 作っているあいだの通信が、自分のページ以外に 0件。
  - この2つを ui_check で確かめる。
- vendor に置き、版と SHA-256、Apache 2.0 の文と OR-Tools の NOTICE を入れる。
