第2版（2026-10-31、確かめ役と決めた）：A 仕上げで変えないものの書き方をそろえた（3 章）、B 何も動かしていないときの「1分で作る」との比べを足した（5 章 C）、C `deviceMemory` が無いブラウザでの Worker の数を足した（4 章）、D「ここまでの答えで終える」の約束を足した（4 章）。相談の答えを 7 章に書いた。

## 0. まとめ

- 手順5 の「じっくり作る（本番。最大10分ほど）」を使えるようにします。合計 約600秒。
- Worker を「CPU の数 − 1」本（最大4本、少なくとも1本）使い、何通りかの解き方を同時に動かします。
- 1本目は、まず「1分で作る」とまったく同じ計算をして **1分の答え（保険）** を作り、そこから「エラーを自動で直す」と同じ解き直しを重ねます。
- 終わりに、候補ごとのいちばん良い答えに **仕上げの入れ替え** をかけ、説明書 3 節の並べる順（`compareResults`）でいちばん良いものを選びます。1分の答えも選ぶ候補に入れるので、1分の答えより悪い答えは選びません。
- **変えないもの**：1分で作る・エラーを自動で直す（上限 10・25・50）・途中から作り直す の計算と答え。じっくり作るのための変更は、じっくり作るの中だけで使います（6-3 の「全部」の時間だけは、決め方 H で変えることがあります）。
- 小分け：
  - **6-1** 仕上げの入れ替え（中身と node の道具。画面は変えない）。版の表示 6.1。
  - **6-2** じっくり作る（何通りか同時・1分の保険・時間の見張り・中止・画面・z の締め直し）。版の表示 6.2。
  - **6-3** あとに回したもの（「全部」の時間・見本の報告・必要なら候補 え）。版の表示 6.3。

## 1. 流れ（合計 600 秒のとき）

| 時間 | Worker 1 | Worker 2〜4 |
|---|---|---|
| 0〜60秒 | 「1分で作る」と同じ計算（種の決め方も同じ・60秒）→ **1分の答え（保険）** | 候補 い・う・い2 を、はじめから長く解く |
| 60〜570秒 | 候補 あ：いまのいちばん良い答えから、解き直しを重ねる | 続き |
| 570〜595秒 | 仕上げの入れ替え（候補ごとのいちばん良い答えに、Worker ごとに同時にかける） | 同じ |
| 595秒 | 届いた全部の答え（1分の答えも入れる）から、並べる順でいちばん良いものを選ぶ | |

- Worker は、良い答えが見つかるたびに、その表を画面の側へ送ります。画面の側は `check.js` で数え、「いまのいちばん良い答え」を小窓に出します。
- **時間の見張り**：600秒＋20秒たっても終わらない Worker は、画面の側で止め、それまでに届いた答えから選びます（スマホで画面が裏に回って計算が遅れたときなど）。
- 1分の答えが段1で作れなかった（時間内に答えが無い）ときも、ほかの候補は段1に長い時間を使えるので、答えが出ることがあります。どの候補にも答えが無いときだけ「時間内に作れませんでした」と出し、表は前のままにします。
- 計算は写しで行い、入れる前にデータが変わっていないか確かめます（いまの 1分で作ると同じ）。入れるときは「自動で作った表」として履歴に入り、元に戻せます。置きかえる前の控えも、いまと同じに残します。

## 2. 何通りかの解き方（候補）

| 候補 | 中身 | 変えるもの |
|---|---|---|
| **あ** 1分から直しを重ねる | 1分の答えから、「エラーを自動で直す」と同じ解き直し（変わるマスの上限 10 → 25 → 50 をくり返す、1回 20秒、回ごとに種を変える）。良くなったとき（`isImproved` で改善、かつ並べる順で良い）だけ、次の出発点にする | 時間の配分（短い解き直しを何回も）・種 |
| **い** 長く解く | 段の順番は 1分と同じ。合計 570秒の配分（段1 ≦ 95秒・段2〜5 あわせて ≦ 285秒・残りを「できれば」の段へ）。「絶対」の段が 1分で時間切れになるような大きい月でも、解ききれる時間を取る | 時間の配分・種（1分と違う種） |
| **う** 数え方に近い式 | い と同じ時間で、「できれば」の段に、責任者の順位と、休みをはさむ時間帯の切り替え（6 章）を入れた式で解く | 式・種 |
| **い2** 長く解く（別の種） | い と同じで、種だけ違う。4本目の Worker 用 | 種 |
| **え** 件数を先に減らす（6-3。決め方による） | 人員不足の段のあとに「絶対」の件数を数える段を入れ、並べる順（件数が先、量があと）に合わせる | 段の順番 |

- 種：1分の答えは、いまの 1分で作ると同じ「作った記録の数 + 1」。い・う・い2 は、それに 1・2・3 を足したもの。あ の解き直しは 10 から先を回ごとに使います。
- **段の順番そのもの（6連勤以上 → 人員不足 → 公休 → 連勤 → …）は変えません。** 並べる順でも上の段の決まりが先に比べられるので、上の段を後ろに回した答えは、ほとんど選ばれないためです。順番を変えるのは、並べる順に合わせる え だけです。
- **え は作るのに手間がかかるので、6-2 の測り C で「あ・い・う・い2 のいちばん良い答えが、見込みの最低件数（`lowerBound`）の『絶対』に届かない月」が 18か月のうち 5か月以上（1/4 以上）あったときだけ、6-3 で作ります。**（量は同じまま件数が増えることがある、の「あとで直すこと」もこれで扱います）
- Worker が少ない機械では、上の候補から順に使います（あ はいつも1本目。残りの順は測り D で決める）。

## 3. 仕上げの入れ替え（6-1）

**変えないもの**（どちらの入れ替えでも）：各人の「出勤の日数・公休の日数・有給の日数・余り日の日数」と、各日の「シフトごとの人数」。同じ日の出勤どうしの入れ替えでは、各人のシフトごとの日数（例：早番の日数）は変わります。

**入れ替えの種類**

1. **同じ日の出勤どうし**：ある日に p さんがシフト S、q さんがシフト T（S と T は違う）→ p さんが T、q さんが S。2人とも、入るシフトを担当できること。
2. **2人×2日のたすき掛け**：p さんが 1つ目の日に X・2つ目の日に Y、q さんが 1つ目の日に Y・2つ目の日に X（X・Y はシフト・公休・有給・余り日のどれかで、違うもの）→ 2人の、その2日を入れ替える。2人とも、入るシフトを担当できること。

**動かさないマス**：固定したマス（錠）・希望のマス・半休・空き・明け・夜勤（夜勤を動かすと、次の日の明けがずれるため）。日ごとに要るスキルが無い人には、そのシフトを入れません。

**入れる決め方**：写しの表に当てて `check.js` で数え、次の2つが両方そろうときだけ入れます。

- `isImproved(前, 後)` が「改善」。
- 並べる順（`compareResults`）でも、前より良い（人員不足を「できれば」にしたときも、並べる順の上の数が増えないように）。

`isImproved` は、あとの表の6連勤以上がどれも、前の表のどれか1つの6連勤以上の範囲の中にあるときしか「改善」と言いません。そのため、**6連勤以上を新しく作る・長くする・2つをつなげる入れ替えは入りません。** 6連勤以上の数も、「絶対」のどの決まりの件数も増えません。

**探し方**：エラーの印があるマスにかかわる入れ替えから試します（その人の、その日の前後6日と、同じ日のほかの人）。1つ入れたら数え直して続け、良くなる入れ替えが無くなるか、時間の上限（じっくり作るでは 25秒）で止めます。乱数は使いません（同じ表なら同じ答え）。入れるたびに必ず良くなるので、同じ所を行ったり来たりしません。

**道具**

- `tools/finish.mjs ファイル.json [--seconds 25]`：仕上げの前後の件数・入れた入れ替えの一覧・かかった秒。
- `tools/finish-stress.mjs`：乱数の月・乱数の手直しをした表に仕上げを当て、次を確かめます。
  - 各人の 出勤の日数・公休の日数・有給の日数・余り日の日数 が同じ。各日の シフトごとの人数 が同じ（3 章のはじめの「変えないもの」の2つ。シフトごとの各人の日数は数えない）。
  - 動かさないマスが1つも変わっていない。担当外のシフト・日ごとに要るスキル・夜勤の次の日 のエラーが増えていない。
  - 入れた入れ替えが、1つずつ `isImproved` で改善、かつ並べる順で良い。
  - あとの6連勤以上が、どれも前の6連勤以上の範囲の中にある（`isImproved` とは別に、道具の中で数え直して確かめる）。
- `tools/check.mjs` に、小さな月で「この入れ替えは入れる・これは入れない（6連勤以上がつながる・長くなる など）」の例を足します。

## 4. 中止・CPU・メモリ・スマホ

- **Worker の数**：CPU の数（`navigator.hardwareConcurrency`）− 1。最大4本、少なくとも1本。CPU の数が分からないときは1本。候補の数より多くはしません。
- **メモリ**：`navigator.deviceMemory` が分かる機械（Chrome・Edge）で 2GB 以下なら1本、4GB 以下なら2本まで。`deviceMemory` が無いブラウザ（Safari・Firefox など）では、タッチだけの機械は2本まで、それ以外は CPU の数から決めます。タッチだけの機械（スマホ・タブレット。`pointer: coarse` でマウスが無い）は、`deviceMemory` があってもなくても2本まで。6-2 で、50人×31日の1本が使うメモリのいちばん多い所（HiGHS の WebAssembly のメモリの大きさ）を node で測り、4本ぶんが 1GB を超えるなら、本数の上限を下げます。
- **1本のとき**：あ だけ（1分の答え → 解き直しを重ねる → 仕上げ）。小窓に「このパソコンでは、1通りずつ探します」と出します。
- **Worker が作れない・途中で止まった**：残りの Worker で続けます。全部が止まったら、届いた答えから選びます。届いた答えも無ければ「計算の部品が止まりました。シフト表は前のままです」。
- **中止**：全部の Worker を止め（`terminate`）、届いた答えは捨てて、表は前のままにします（説明書 4 節）。ui_check で、中止のあと動いている Worker が 0本（Playwright の `page.workers`）・データが1文字も同じ、を確かめます。Worker の数は、ui_check で `hardwareConcurrency` を 1・2・4・16 に変えて、1・1・3・4本になることを確かめます。`deviceMemory` を 2・4 にしたとき（1・2本まで）と、`deviceMemory` を無くしたとき（CPU の数から）も確かめます。
- **ここまでの答えで終える**（中止とは別のボタン）：
  - 1分の答え（保険）ができるまでは押せません。押せない理由を、ボタンの近くに「1分の答えができると押せます」と出します。
  - 押したら、ほかの Worker を全部止め、いまいちばん良い答え（1分の答えも入れて、並べる順で選ぶ）を、ふつうに作り終えたときと同じ流れで入れます（入れる前の控え・別のタブで変わっていないかの確かめ・`record` で元に戻せる・作った記録）。作った結果には「途中で終えました（◯秒）」と書きます。
  - 「中止」（反映しない・赤いボタン）と取り違えないよう、色と言葉を分けます（「ここまでの答えで終える」はふつうの色のボタン。小窓に「中止は、作った答えを入れずに終わります」「ここまでの答えで終えると、いまのいちばん良い答えを入れます」と書く）。
  - ui_check で、1分の答えの前は押せない／押すと答えが入り、Worker が 0本になり、元に戻すで作る前の表に戻る、を確かめます。
- **計算中の小窓**：いまの段階（「1分の答えを作っています（保険）」→「何通りかで、より良い答えを探しています（◯通り同時）」→「仕上げをしています」）、1分の答えの件数、いまのいちばん良い答えの件数、「◯秒たちました（あと最大◯秒）」、「中止」。注意書き：「計算のあいだは、ほかの重いアプリを閉じてください。画面を閉じたり、ほかのアプリに切り替えたりすると、計算が止まることがあります」。
- **作った結果**：「『じっくり作る』で作りました（◯秒・◯通り）」と、1分の答えからどう変わったか（例「できれば 40件 → 18件」）。1分の答えのほうが良かったときは「じっくり探しても、1分の答えより良い答えはありませんでした（1分の答えを使っています）」。「最後まで解ききった」と書くのは、いまと同じく、選んだ答えの全部の段が「解ききった」ときだけです（あ の解き直しは変わるマスを限っているので、選んだ答えが あ のときは書きません）。仕上げで変わったときは「仕上げの入れ替えで、さらに◯件減らしました」。
- **記録**：`month.runs` に、作り方 `careful`・時刻・候補ごとの結果（件数・秒・段の状態）・選んだ候補・1分の答えの件数・仕上げで入れた数 を足します（いまと同じく 20回ぶんまで）。
- 選ぶ画面：はじめは「1分で作る」が選ばれている（いまと同じ）。「じっくり作る」の説明は「最大10分ほどかかります。いちばん良い答えを、何通りかで探します」。
- 確かめの道具だけが、アドレスの `?careful=20` で 600秒を短くします（10〜600秒。1分の答えの秒は `?seconds=` のまま）。
- 計算の中身は `app/js/solver/careful.js` に置き、Worker を作る関数を渡して動かします。ブラウザでは Web Worker、node の道具では worker_threads で、同じ中身が動きます（stages.js に HiGHS を読み込む関数を渡すのと同じ考え方）。

## 5. 測り方と、採るか捨てるかの決め方（測る前に決める）

このパソコンは CPU 16（8コア）・メモリ 16GB です。アプリでは Worker 4本になります。じっくり作る（4本）は、同時に2つまで（8本 = 8コア）で測ります。

| 測り | データ・回数 | 決め方 |
|---|---|---|

| **B** 仕上げ（6-1） | 見本3つ × 12か月 ＋ 作り物 12通りを 60秒で作った 1分の答え（各3回。保存して使うので、仕上げは何度でも同じ結果）＝ 144 表 | 3 章の確かめの破れ 0（必須）。できれば が平均 1件以上減り、かつ半分以上の表で減る → じっくり作るで使う。50人×31日で 25秒以内に止まらなくても、上限 25秒で切る。減らなければ、使わずに相談 |
| **C** じっくり作る 全体（6-2） | 見本3つ × 4か月（2026年11月・2027年2月・5月・8月）＋ 作り物 6通り（8人28日・15人30日・25人31日・50人31日・人手が足りない月・固定の無い月）＝ 18か月 × 3回、600秒、Worker 4本 | 必須：どの回も、選んだ答えが、その回の1分の答えより並べる順で悪くない（破れたら不具合）。報告：1分の答えとの比べ（6連勤以上・絶対・できれば の平均、良くなった回の数）、見込みの最低件数に届いた月の数。**あわせて、同じ 18か月で、ほかに何も動かしていないときの「1分で作る」（同じ条件で3回）も作り、じっくりの答えと並べる順で比べて、良い・同じ・悪い の回数を書く（合否にはしない）。悪い回があれば、その月と理由を書く** |

| **F** z の締め直し（6-2） | C と E の全部の回 | 締め直した量 ≦ 締め直す前の量、かつ正しく数える決まり（6連勤以上・人員不足・公休が足りない・連勤超過 など）で 式の量 = 検査の量。破れ 0 で採る |

| **H** 「全部」の時間（6-3） | B と同じ 144 表に「エラーを自動で直す」の「全部」を 15・30・60秒で | 「全部」の案が改善になる表が 8割以上、かつ「全部」の案の できれば が 上限50 の案以下になる表が半分以上、の両方を満たす いちばん短い時間にする。どれも満たさなければ 15秒のままにして相談（「全部」を外して、じっくり作るを案内する など） |

## 6. あとに回したものの決め方（案）

| もの | 案 |
|---|---|
| 時間帯の切り替え回数の式 | **1分の式は変えません**（1分の答えが変わり、3-3 の測り直しが要るため）。じっくり作るでは、仕上げ（`check.js` の数え方そのもので減らす）と、候補 う で減らします。う の式：人×日×時間帯に「最後に出た時間帯」を表す 0〜1 の数 L を足し、L[日,G] ≧ 出勤[日,G]、L[日,G] ≧ L[日−1,G] − その日の出勤、切り替え ≧ 出勤[日,G] + L[日−1,G′] − 1（G と G′ は違う時間帯）。check.js の数え方に合わせ、式の量 = 検査の量 を道具で確かめます。う が D で残れば、1分にも入れるかを「あとで直すこと」に書きます |
| 「全部」の上限の時間 | 測り H で決めます（6-3） |
